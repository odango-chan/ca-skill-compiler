# JSON Schema v0.1 support boundary

Updated: 2026-11-12. This matrix separates validation of a JSON Schema document from the Compiler's ability to prove a Producer satisfies a Consumer. The implementation targets selected Draft 2020-12 semantics and fails closed where it cannot prove compatibility; it is not a general-purpose JSON Schema evaluator.

## Result categories

- **Schema validation** checks whether imported Schema syntax and keyword values are well-formed for the implemented structural contract. Invalid or unsupported document shapes produce `LIB_SCHEMA_INVALID`.
- **Binding proof** checks only whether a known Producer is guaranteed to satisfy a Consumer. Unsupported proof constructs produce `BINDING_UNSUPPORTED`; a proven incompatibility produces `BINDING_TYPE_MISMATCH`.
- **Annotation** means a keyword does not constrain instance validity under the default Draft 2020-12 vocabulary. It must not be used as a type or value proof.

## Keyword matrix

| `format` | **SUPPORTED** as a string-valued annotation under the default Draft 2020-12 vocabulary | **ANNOTATION**: it does not constrain bindings and is not treated as type proof. A separately selected format-assertion vocabulary is not implemented | `TestSchemaFormatAnnotationDoesNotConstrainBindings` |

The generic Schema shape validator accepts Boolean Schemas at the document root and in nested positions. The v0.1 ToolCatalog envelope separately restricts operation-level input/output/reconcile Schema roots to objects; local `x-common` fragments may be Boolean and are valid in nested positions. Literal checks accept any JSON value for `true` and none for `false`; Producer implication handles their universal-set and empty-set semantics. `TestToolCatalogRootSchemaContractMatchesImporter` and `TestToolCatalogAllowsBooleanSchemaFragmentsInXCommon` pin this boundary. Annotation-only Schemas (including `format`, `contentEncoding`, and `contentMediaType`) are treated as unconstrained for binding.

The Schema shape validator recognizes additional Draft 2020-12 annotations and `contentSchema`; their application semantics are not used as binding proof. Unknown keywords fail closed. `$vocabulary` and non-default assertion vocabularies are not implemented.

## Current official-source consequence

The PDU Skill currently has one proven binding mismatch in addition to three unsupported regex implications: its Script Output declares `minLength: 1` for `operationContextRef` and `policyResultRef`, while the Tool Consumer also imposes `maxLength: 512`. Since the Script Output does not guarantee that upper bound, the Compiler reports `BINDING_TYPE_MISMATCH`. This is a Skill-owned Output contract gap, not a missing Owner Schema or a Compiler defect. Its fixed `profileRef` value now correctly proves against the Tool's type-less `const` schema.
