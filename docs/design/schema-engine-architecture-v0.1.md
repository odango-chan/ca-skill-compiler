# Schema Engine Architecture v0.1

**Status:** Proposed architecture for review; design only. No implementation migration is authorized by this document.
**Date:** 2026-11-12
**Scope:** `ca-skill-compiler` v0.1 Core, based on the implementation in PR #5.
**Parent implementation:** `feat/compiler-v01-implementation-20261111` at the reviewed snapshot.

## 1. Decision summary

The Compiler MUST NOT grow into a general-purpose, independently maintained JSON Schema implementation.

The intended boundary is:

1. YAML remains the human-authored serialization format for ToolCatalog and Skill-owned Schema documents.
2. The Schema language and semantics are JSON Schema Draft 2020-12. YAML is not a second Schema language and the Compiler MUST NOT introduce a proprietary Schema DSL.
3. A mature Go JSON Schema implementation is responsible for standard Schema compilation and JSON instance validation, subject to a Native/WASM compatibility spike.
4. Compiler-owned project policy remains in the Compiler: source ownership, allowed reference boundaries, deterministic diagnostics, and in-memory-only resource access.
5. Producer-to-Consumer compatibility is a separate static data-flow proof. A general JSON Schema validator does not automatically provide implication/subsumption proof between two schemas. The Compiler retains a deliberately bounded, conservative proof engine for this purpose.
6. Script Output Schema generation remains a Compiler responsibility because it translates the pinned Script Contract's statically understood Python type declarations into JSON Schema.

This is a boundary correction, not a wholesale rewrite. Existing behavior and fail-closed guarantees are preserved unless an explicit later design decision changes them.

## 2. Current implementation baseline

The reviewed PR #5 implementation has these relevant components:

| Current location | Current responsibility | Proposed disposition |
| --- | --- | --- |
| `internal/compiler/schema_validation.go` | Hand-written Schema keyword/type/shape validation, JSON literal checks, numeric constraints | Replace standard Schema document validation with a library-backed adapter. Retain only YAML-to-JSON boundary checks and Compiler policy checks that are not JSON Schema semantics. |
| `internal/compiler/schema_refs.go` | Project-local JSON Pointer resolution, recursive expansion, ownership checks, cycle rejection | Split policy from mechanics. Retain path normalization, project membership, ownership, cycle/resource limits, and no-network policy. Prefer the library's reference compiler/resolver for standard reference semantics, backed only by an in-memory project resource registry. |
| `internal/compiler/bindings.go` | Producer discovery, scope/data-flow analysis, literal checks, and Producer/Consumer compatibility | Preserve the data-flow analysis. Refactor schema access behind a normalized read-only Schema model and keep a documented proof subset. Do not delegate implication proof to an instance validator. |
| `internal/compiler/scripts.go` | Static Python contract parsing and generated Script Output Schema | Preserve. Generated output remains ordinary Draft 2020-12 JSON Schema represented in the existing artifact format. |
| `internal/compiler/library.go` and ToolCatalog parsing | Import caller-supplied YAML ToolCatalog and expose Operations | Preserve the caller-supplied catalog model. Do not create or fetch a second ToolCatalog source. |

At the reviewed snapshot, `go.mod` directly requires `gopkg.in/yaml.v3`; no JSON Schema engine is currently a direct dependency. The hand-written structural validator recognizes a substantial keyword set, while the binding matrix explicitly marks multiple applicators and other features unsupported for implication proof. This distinction must remain visible in diagnostics and documentation.

## 3. Ownership and source of truth

### 3.1 Schema document ownership

- Tool input/output schemas are owned by the supplied ToolCatalog, whose authoritative contract/source remains with the Tool owner (currently `ca-agent-demo`).
- Host, Observation, and other externally supplied context schemas are owned by their respective Host/contract owner.
- Skill-specific request or domain schemas are owned by the Skill that declares them.
- Script Output schemas are generated by Compiler from the pinned Script Contract and the Script's statically declared output type.
- Compiler MUST NOT invent missing Owner schemas, infer missing Tool output fields from implementation code, or silently manufacture fallback contracts.

The existing ToolCatalog YAML files in `ca-agent-demo` are the reference for real Operation contracts. The Compiler consumes the complete files supplied by its caller; it does not reach into `ca-agent-demo` at build time and does not duplicate those contracts as Compiler-owned definitions.

### 3.2 Serialization versus semantics

| Concern | Contract |
| --- | --- |
| Authored document format | YAML |
| Schema semantic standard | JSON Schema Draft 2020-12 |
| YAML parser | Existing `gopkg.in/yaml.v3` boundary |
| Engine input | JSON-compatible value/document or equivalent library-native representation |
| Generated Schema semantics | Draft 2020-12 |
| Generated artifact serialization | Preserve the existing BuildResult path/format contract; do not change it as part of engine migration |

JSON Schema is a data model and semantic specification, not a requirement that authors write JSON files. YAML documents must map unambiguously to JSON values. YAML-only values (custom tags, timestamps as non-JSON values, non-string mapping keys, non-finite numbers, unsupported alias constructions, and duplicate mapping keys) MUST be rejected rather than coerced silently.

Numeric values MUST retain exact JSON number meaning across YAML parsing, Native, WASM, and generated output. Do not route values through binary floating point when doing so changes their decimal representation or compatibility result.

## 4. Target architecture

```text
Caller BuildRequest.files (complete in-memory file set)
                 |
                 v
        YAML / source boundary
        - parse YAML
        - reject duplicate keys and non-JSON values
        - preserve source path and line/column
                 |
                 v
        Project Schema Registry
        - canonical project-relative paths
        - ownership and reference policy
        - immutable in-memory documents
        - no filesystem/network access
                 |
                 v
        Schema Engine Adapter
        - Draft 2020-12 selection
        - standard Schema compilation
        - standard JSON instance validation
        - engine errors -> Compiler diagnostics
                 |
         +-------+----------------------+
         |                              |
         v                              v
  Schema validity                 Compiler semantic analysis
  and literal checks              - Producer discovery
                                  - Scope / dominance / aliases
                                  - Producer -> Consumer proof
                                  - Script Output generation
                                  - Procedure / Skill linking
```

### 4.1 YAML / source boundary

A single conversion boundary MUST be used by Native and WASM. It MUST:

- Parse the authored YAML once per source file and preserve the source filename and node locations.
- Reject duplicate keys, non-string JSON object keys, unsupported YAML tags/types, invalid/non-finite numbers, and values that cannot be represented as JSON.
- Resolve YAML aliases safely with bounded traversal and cycle detection; aliases are YAML syntax, not JSON Schema references.
- Preserve exact integer/decimal values. Any engine representation conversion must be covered by precision regression tests.
- Keep original YAML nodes or an equivalent source map available for diagnostics and Compiler-specific source navigation.
- Avoid changing Skill/ToolCatalog authoring files or requiring authors to write JSON.

### 4.2 Project Schema Registry and reference policy

Compiler policy is stricter than generic JSON Schema URI resolution. The registry MUST enforce:

- Every referenced document is part of the caller-supplied in-memory BuildRequest.
- Remote references, filesystem references, absolute paths, path traversal, unsupported URI forms, and references outside the allowed project root are rejected.
- Library-owned Schema references remain within the Library ownership boundary.
- Skill-owned Schema references cannot cross into another Skill's private ownership boundary. Any explicitly permitted shared location must be defined by the existing contract, not inferred.
- Cycles and excessive reference depth/document count fail deterministically with a Compiler diagnostic.
- No DNS, HTTP, filesystem, environment, or other external resolution is permitted.
- Reference resolution is deterministic regardless of BuildRequest file ordering.

The preferred design is to let the selected JSON Schema library perform standard reference compilation while providing it a custom in-memory-only resource loader/registry. If the library cannot provide a provably closed resolver, the adapter may perform a constrained linking/preflight pass, but MUST NOT reimplement the full JSON Schema evaluator. The spike must decide this based on actual library APIs and tests.

The registry owns *which resources may be loaded*. The Schema engine owns *what a valid Draft 2020-12 reference means*. These concerns must not be conflated.

### 4.3 Schema Engine Adapter

Compiler code MUST depend on a small internal interface, not on a third-party library's types throughout the codebase. The exact Go signatures are implementation details, but the logical operations are:

- Compile a Schema document with its canonical in-memory resource context.
- Validate a concrete JSON-compatible instance against a compiled Schema when a concrete value is available.
- Return structured errors that can be mapped to stable Compiler diagnostics and source locations.
- Expose only the limited introspection needed by the binding analyzer, or hand it a normalized immutable Schema representation.

The adapter MUST pin the Draft 2020-12 dialect. It MUST NOT silently accept a different dialect or enable optional assertion vocabularies without an explicit contract decision.

The engine MUST NOT be given a default network/file loader. All resource loading must route through the project registry.

### 4.4 Producer / Consumer compatibility analyzer

This remains Compiler-owned.

Its purpose is to prove that every value produced by a statically known source is guaranteed to satisfy the consuming Tool/Procedure/Script/Predicate input contract. This is a set-inclusion question:

`ProducerSchema ⊆ ConsumerSchema`

It is not equivalent to checking a few sample instances, nor is it solved by compiling both schemas with a validator.

The analyzer MUST:

- Preserve the current Procedure data-flow model: node outputs, nested step scopes, Procedure inputs, explicit Host/Observation sources, aliases, and node-output dominance.
- Use a documented, deliberately bounded subset for schema implication.
- Return one of: proven compatible, proven incompatible, or unsupported/unprovable.
- Emit `BINDING_TYPE_MISMATCH` only when incompatibility is actually established.
- Emit `BINDING_UNSUPPORTED` when the proof would require unsupported semantics; never downgrade uncertainty into success.
- Keep JSON Schema document validity separate from binding proof capability.
- Reuse the normalized Schema representation and exact-number handling from the adapter; do not create a second YAML parser or a second definition of JSON Schema syntax.
- Keep literal checking correct for boolean schemas, omitted `type`, `const`, `enum`, and the currently supported numeric/object/array/string constraints.

The initial migration MUST preserve the current proof subset and diagnostics. Expanding the proof subset is a separate workstream, not a side effect of adopting a more complete validator.

### 4.5 Script Output Schema generation

The Compiler remains responsible for statically parsing the supported Script Contract and generating strict Output Schemas. It MUST:

- Continue to avoid executing Python.
- Preserve current TypedDict, nested TypedDict, primitive, list, Literal, NotRequired, and Annotated behavior where currently supported.
- Emit standard Draft 2020-12 Schema semantics.
- Validate generated schemas through the same Schema Engine Adapter used for imported schemas.
- Preserve deterministic output paths, serialization, and Native/WASM byte parity.

## 5. Candidate library evaluation

The prior discussion identified `github.com/santhosh-tekuri/jsonschema/v6` as a candidate, not an approved dependency. No library is selected by this design document.

Evaluate at least the candidate above and one viable alternative against the same spike. The evaluation MUST verify, rather than assume:

1. Draft 2020-12 support and dialect selection.
2. Schema compilation, boolean schemas, local and cross-document references, and reference cycles.
3. Ability to provide a closed, in-memory-only resolver with no network/filesystem fallback.
4. JSON instance validation semantics for the keywords used by the official ToolCatalog and Skill schemas.
5. Exact-number behavior for large integers and decimal/exclusive/multipleOf boundaries.
6. Go/WASM compilation and execution in the actual browser Worker environment.
7. Package dependency footprint and resulting WASM artifact size.
8. Compilation/validation latency and memory on the pinned official project and synthetic adversarial inputs.
9. Error structure/stability sufficient to map into Compiler diagnostics.
10. License, maintenance status, supported Go versions, and transitive dependency risk.

A library's support for Draft 2020-12 MUST NOT be interpreted as support for ECMA-262 regular-expression semantics or for Producer/Consumer implication unless independently demonstrated.

### 5.1 Spike output

The spike is a small isolated package or branch. It MUST NOT refactor `bindings.go` or change the public BuildRequest/BuildResult contract.

It must produce:
- A candidate comparison table with source links and tested versions.
- A Native and WASM build/runtime result for each candidate.
- A closed-resolver test proving a remote reference cannot trigger external access.
- A golden corpus run against current Schema documents and literals.
- Precision and malformed-YAML regression results.
- WASM size and basic performance measurements.
- A recommendation: adopt one candidate, reject both with evidence, or identify a narrowly scoped blocker.

No dependency is added to the main Compiler path until the spike is accepted.

## 6. Internal API boundary (illustrative)

The adapter should expose compiler-owned types. This is a conceptual shape, not a requirement to copy these exact declarations:

```go
type SchemaDocument struct {
    Path       string
    Root       *yaml.Node
    SourceMap  SourceMap
    CanonicalURI string
}

type SchemaEngine interface {
    Compile(document SchemaDocument, registry SchemaRegistry) (CompiledSchema, error)
    Validate(instance JSONValue, schema CompiledSchema) error
}

type SchemaRegistry interface {
    Resolve(fromPath, reference string) (SchemaDocument, error)
}
```

Third-party library types MUST remain inside the adapter package. Compiler diagnostics, BuildRequest, BuildResult, and Native/WASM APIs MUST NOT expose those types.

The actual implementation may choose a more efficient representation than `yaml.Node`; it must retain source mapping, exact JSON values, deterministic resolution, and Native/WASM parity.

## 7. Migration plan

### Phase 0 — Freeze and inventory (design prerequisite)

- Freeze this ownership and responsibility boundary.
- Inventory all call sites of `validateSchemaShape`, `expandSchemaRefs`, `schemaProperty`, literal validation, and Producer/Consumer compatibility helpers.
- Map every current test to one of: YAML/source boundary, standard Schema validity, reference policy, instance validation, binding proof, Script generation, or parity.
- Record current Native diagnostics and WASM goldens for the pinned official source snapshot.
- Do not add more hand-written JSON Schema keywords during this phase.

### Phase 1 — Library spike

- Evaluate candidates as described in §5.
- Verify WASM Worker behavior, exact numbers, and resolver closure.
- Do not alter current production behavior or the public API.
- Make a documented go/no-go decision.

### Phase 2 — Adapter introduction

- Add the selected dependency only after Phase 1 acceptance.
- Implement the adapter and project registry behind compiler-owned interfaces.
- Run the existing Schema validity and literal corpus through the adapter.
- Preserve current diagnostics where practical; document intentional diagnostic mapping changes.
- Keep the old implementation available only as a temporary test oracle if needed. Do not ship two active production engines.

### Phase 3 — Standard semantics cutover

- Route imported and generated Schema document validation through the adapter.
- Route concrete JSON literal/instance validation through the adapter where semantics are standard JSON Schema.
- Remove duplicated standard keyword shape/type validation and duplicate standard reference evaluation once parity gates pass.
- Retain project ownership/reference policy in the registry.
- Retain Compiler-specific binding implication in the semantic analyzer.

### Phase 4 — Binding analyzer refactor

- Replace direct dependence on raw YAML traversal with the normalized Schema model incrementally.
- Preserve all current positive and negative binding cases.
- Keep unsupported implication constructs fail-closed.
- Do not expand implication coverage in the same change unless separately reviewed and proven.

### Phase 5 — Remove legacy code and close acceptance

- Remove superseded hand-written standard Schema validator/reference evaluator.
- Keep only YAML boundary, project policy, and Compiler-specific static proof code.
- Run Native, WASM, Chromium Worker, official source, adversarial, and deterministic-output suites.
- Update `docs/workstreams/json-schema-support-v0.1.md` to reflect the new separation and exact supported proof subset.

## 8. Compatibility and acceptance gates

Migration is accepted only when all applicable gates pass:

| Gate | Required evidence |
| --- | --- |
| YAML compatibility | Existing ToolCatalog and Skill-owned YAML Schemas parse without authoring-format changes. Duplicate keys and non-JSON YAML values fail closed. |
| Draft semantics | Boolean schemas, omitted `type`, `const`, `enum`, object/array constraints, annotations, and supported applicators match Draft 2020-12 behavior. |
| Reference safety | Local references resolve from the supplied file set; remote, absolute, traversal, cross-owner, cyclic, and missing references are rejected without external access. |
| Numeric fidelity | Large integers, exact decimals, exclusive bounds, and `multipleOf` have matching Native/WASM results. |
| Binding preservation | Existing Producer/Consumer positive, mismatch, and unsupported goldens remain correct. No uncertainty is accepted as success. |
| Script output | Generated schemas remain valid and deterministic; existing TypedDict fixtures retain their output paths and bytes unless a documented serialization-only change is approved. |
| Native/WASM parity | Same request yields same diagnostics, output paths, order, and bytes. |
| Browser runtime | Actual WASM Worker smoke tests pass in Chromium; a successful WASM build alone is insufficient. |
| Footprint/performance | WASM size and runtime/memory are measured and accepted against recorded baseline. |
| Regression | `GOWORK=off go test ./... -count=1`, `go vet ./...`, Native build, WASM build, Chromium tests, official pinned corpus, and `git diff --check` pass. |

## 9. Explicit non-goals

This work does not:

- Change YAML ToolCatalog authoring to JSON.
- Define a new YAML Schema DSL or proprietary keyword set.
- Move Tool contract ownership into Compiler.
- Fetch Tool contracts from `ca-agent-demo` during compilation.
- Add a package manager, dependency resolver, lockfile, remote registry, or cache.
- Execute Python or Tools.
- Change Skill Language v0.2, BuildRequest, BuildResult, CLI commands, or Studio integration.
- Claim complete arbitrary Schema implication between Producer and Consumer.
- Weaken fail-closed behavior to make the official examples pass.
- Fabricate missing Host/Observation Owner schemas or missing MAS Operations.

## 10. Review questions and decision record

Before implementation, reviewers should explicitly confirm:

1. YAML remains the authoring/serialization format; Draft 2020-12 is the only Schema semantic contract.
2. ToolCatalog remains caller-supplied and owned by its source repository; Compiler does not package-manage or fetch it.
3. The standard Schema engine is replaceable behind an adapter and has no direct dependency on Compiler public APIs.
4. The project registry is the only resource resolver and cannot access network or filesystem.
5. Producer/Consumer implication remains Compiler-owned and conservative.
6. The library choice is deferred until Native/WASM, precision, resolver, footprint, and behavior tests pass.
7. Current PR #5 implementation work is not interrupted or overwritten; this document defines a follow-on design/migration workstream.

**Decision:** Proposed. Design review required before Phase 1/2 implementation. No code migration is authorized by this document.
